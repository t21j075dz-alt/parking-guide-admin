# 2026-10-29 録画実演の判定を「空き→駐車中→停車中→出庫中→空き」に統一

実際の2026-10-29 20:32〜20:42の録画判定動画（598.4秒）と診断CSVを調査したところ、ほぼ全区画が初期`unknown`、3番の車を4番にも誤って`occupied`としたり、3番が`available`と`unknown`を往復する現象があった。従来の推論は車体下半分の複数点による区画推定と停止判定だったが、**隣の区画に車体画像がかかった場合も影響**していた。

今回、**録画実演専用**の`recorded_parking_states.py`で新しい段階判定を行う。

| 段階 | 認定条件 | ユーザーアプリでの案内対象 |
|---|---|---|
| 空き | 録画実演開始時の初期値・出庫完了後 | 空き区画として候補 |
| 確認中 | 車体下端らしき部分を検出、5秒の継続確認前／複数区画で曖昧 | **案内しない** |
| 駐車中 | 同一車両の下端が同一区画内に5秒以上継続し、移動を観測 | **案内しない** |
| 停車中 | 同一区画内で車体下端がほぼ動かない状態を約5秒確認 | **案内しない** |
| 出庫中 | 停車していた同一車両が動き始め、車体下端が区画を出た状態を連続確認 | **案内しない** |
| 空きに復帰 | 同一車両が区画外を移動し続け、1.5秒以上の退出を確認 | 空き区画として候補 |

**時間は動画の経過秒数**で測り、デスクトップPCの重い推論による遅れを認定時間に含めない。YOLO検出IDが消えるだけでは「出庫」と断定しない。車体下端は**YOLO検出枠の下側約8%の複数点に基づく近似**であり、タイヤ・車体底面の本物のセグメンテーションモデルを搭載したわけではない。複数区画のどちらにあるか決められない場合は未確認とする。

動画の初期設定はすべて「空き」で開始するが、**撮影当初から実車が存在する区画は、最初に下端が検出されると直ちに「確認中」に変化し、5秒後の判定で停車中へ変わる**。これは録画による研究実演用の初期条件であり、実カメラの物理的な空車証明には使えない。実カメラ`home-test-001`の厳格な`unknown`初期状態は変更しない。

- **Supabase:** `parking_live_status.status`の互換性を保ち、`occupancy_phase`（`available/parking_in/stopped/exiting/unknown`）に録画専用の段階を保存。実カメラのデータと施設IDは完全に分離。
- **表示:** 録画のYOLO判定画面・保存動画には各駐車区画の日本語段階（Windowsの日本語フォントがある場合）、利用者アプリの駐車マップにも「空き／駐車中／停車中／出庫中／確認中」を表示する。
- **診断:** `区画状態の変化.csv`は5列目の`車両段階`を記録する。区画状態の`occupied`が同じでも、`parking_in→stopped`や`stopped→exiting`の切替時に行を書き出す。
- **起動:** 今までどおり`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_video_demo.ps1`。アプリ共有する場合だけ`-Share`を付ける。`-VerifiedEmpty`は不要。

**実地検証が必要:** GitHubの回帰テストでは状態遷移・区画の曖昧な重なり・ID消失・時間計測をテストした。元の`best.pt`モデルがこの環境にはないため、ユーザーがアップロードした動画の新しいYOLO判定結果自体の実測精度は未検証。修正版をデスクトップで動画から再推論し、特に3番と4番の状態が安定したかログを照合する。

# デスクトップPC：録画動画を使ったリアルタイムYOLO判定→駐車場案内（2026-10-29）

## 何ができる？
デスクトップPCのMP4/MOV/AVIなどを「仮想カメラ」として元動画の時刻に合わせて再生し、**その場でYOLO推論** → 車両追跡 → 6区画の占有判定 → 状態共有 → 利用者アプリで区画選択・案内します。録画のCSVを後から単純再生する従来の`recorded-demo.html`とは異なります。

**最優先の安全策：** 録画の判定は現在の空車状況ではないので、物理的な自宅駐車場 `home-test-001` へは絶対に送らず、`home-video-demo-001` という専用施設に送ります。ユーザー画面に「録画YOLO実演・現在の空きではありません」と表示します。動画もスナップショットもクラウド送信しません。クラウドへ送信するのは区画状態と匿名の追跡セッションだけです。

## 初回準備
1. デスクトップのPowerShellで `cd "$env:USERPROFILE\parking-guide-admin"; git pull --ff-only; cd .\parking-vision` と実行。
2. 以前ノートPCからコピーした6区画データ `config_from_laptop.json` と、デスクトップ用 `config.json` が必要です。後者にはSupabaseの接続設定とデスクトップ上で使えるYOLO学習済みモデル`best.pt`へのパスが入ります。**実USBカメラ番号やCamoのカメラを接続・校正し直す必要はありません。**
3. 初回起動時、`prepare_video_demo.py`が2ファイルを結合して`config_video_demo.json`を作成します。`config.json`は変更しません。動画に写る6区画の撮影位置・向きが旧PCの区画登録時と同じ必要があります。元の登録は1280×720（16:9）なので、4:3の動画にはそのまま適用できません。
4. 動画の最初のフレームに重ねた6区画をプレビューで必ず確認。`S`なら続行、`Q`なら停止。位置がずれている動画は再校正が必要です。映像は自動引き伸ばししません。

## 起動方法

**簡単:** `録画動画でYOLO案内を実演.cmd` をダブルクリックして 1＝ローカルテスト／2＝利用者アプリへの録画実演共有を選択します。動画のフルパスは画面で入力できます。

**先にクラウド送信なしで試す（推奨）:**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_video_demo.ps1
```

動画のフルパス入力 → 区画線の目視確認（S） → 録画に合わせたYOLO判定画面が表示されます。診断CSVと判定つき録画は`%LOCALAPPDATA%\ParkingResearch\Recordings`以下の`_VIDEO_DEMO_`フォルダへ保存します。元動画は変更されません。

**利用者アプリに共有する（明示的な選択のみ）:**

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_video_demo.ps1 -Share
```

確認に`録画共有`と入力し、Supabaseの管理者アカウントでログインします。録画の6区画と映像を確認した後、`home-video-demo-001`の公開を一時ONにします。終了・`q`押下時にはOFFへ戻します。実施設`home-test-001`は常に別です。ブラウザーの利用者アプリで **「自宅駐車場（録画YOLO実演）」** を選択すると、通常と同じ案内条件・マップ・区画案内の処理を使えます。

**「空き」として案内する区画を含めたい場合:**
録画の最初のコマで確実に車も障害物も無いと確認できる区画IDだけ、`-VerifiedEmpty`を付けます。プログラムで再度「空き確認」入力を求めます。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_video_demo.ps1 -Share -VerifiedEmpty "space_001,space_002"
```

`space_001`や`space_002`は説明用の例です。**実映像で未確認の区画を指定してはいけません。** 指定なしでは初期状態は`unknown`で、YOLOが車を確認したときは`occupied`になっても、根拠のない「空き」を案内しません。空き判定には連続観測時間が必要です。

## 動画が終わったら
- 自動停止／共有OFF。通常の自宅用の空車情報は変化しません。
- 動画のFPSにYOLOが追いつかないときはフレームを飛ばし、PowerShellにその旨を表示します。映像の時間を止めて「リアルタイム」と偽装しません。
- 実際の利用者が案内先へ到着したことを録画から判断できません。研究でのシミュレーションと本番の実ライブ案内は区別します。
- 実車の認識精度は、使用する動画・画角・夜間照度によって変わります。今回の自動テストはプログラムの処理・安全分離の確認であり、実際の車両認識の正解率を証明するものではありません。

- 元`config.json`、古いバックアップ、モデルパス、Supabaseキーは勝手に変更しません。移行ツールは映像やJSONをクラウドへアップロードしません。

# 2026-10-29 デスクトップ移行で「6区画IDがそろっていません」と出る場合

旧PCバックアップの`space_uids`が1件などになっている可能性があります。`space_uids`は案内対象の番号一覧、`space_zones`は**カメラ映像の四隅座標**です。どちらも必要であり、管理アプリの2Dレイアウトからカメラ座標を自動生成することはできません。

**修正した移行ツール**は移行元を1ファイルに固定せず、`config_backup*.json`、`config_from_laptop*.json`などを検査して「区画ID件数／実際のカメラ四隅の件数／利用可能」を表示する。使えるバックアップが1件なら自動選択し、複数なら番号を選ぶ。

- 四隅座標が`space_001`～`space_006`の6件あり、`space_uids`だけ短くなっていた場合は、区画IDを復元して映像との一致確認に進める。**必ず黄色の枠線が6区画とも合うか確認する**。
- 四隅座標自体が6件ないときは移行を止め、ノートPCから実際に6区画を設定していた`parking-guide-admin/parking-vision/config.json`を取り出し、デスクトップのフォルダへ`config_from_laptop.json`として保存する。**デスクトップの`config.json`を上書きしない。**
- その後、`git pull --ff-only`、`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\transfer_home_zones.ps1`で再実行。
- カメラの位置・画角が違う場合は復元せず再校正。デスクトップのカメラ番号やモデルパス、認証情報は引き続き維持し、空き確認を捏造しない。

ノートPCで設定した自宅駐車場6区画（`space_001`〜`space_006`）は、同じUSBカメラ・設置位置・画角であれば四隅をクリックし直さずに引き継げます。カメラ番号はデスクトップPCで0番になる場合があるため、そのまま以前の番号をコピーしてはいけません。

## 操作

2. ノートPCの`config.json`をデスクトップの`parking-vision`フォルダに**別名で**コピーする（既存のデスクトップの`config.json`を上書きしない）。既に`config_backup_desktop_before_camera.json`に6区画があるならコピー不要。
3. デスクトップ側では`select_external_camera.py`を使い実カメラ番号（例:0）を目視で確認する。**カメラ番号・接続方式が変わると現行の区画登録は初期化されるため、旧PC設定のバックアップを必ず確保する。**
4. `ホーム駐車場_区画を引き継ぐ.cmd`をダブルクリック。または`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\transfer_home_zones.ps1`を実行。自動で`config_backup_desktop_before_camera.json`を読み込む。ない場合はコピーした旧PCの設定のフルパスを入力する。
5. デスクトップUSBカメラに黄色で描画された6区画を確認する。**実際の区画線と完全に一致しないときはQで中止。** 合っているときだけ`S`を押し、PowerShellで`一致`と入力する。
6. プログラムは**区画ID・座標・入口出口だけ**をデスクトップの`config.json`へ保存する。現在のカメラ番号・Python・モデルパス・Supabase設定を保持し、以前の初期空車承認は無効にする。保存前の設定は`config_backup_before_zone_transfer_日時.json`へ退避。

## 移行できない場合
- 元バックアップに6区画がすべて含まれない：旧ノートPCの元の`config.json`または別のバックアップを用意。
- 画像の縦横比が以前と違う：自動転送せず`calibrate.py`で再登録。
- 番号と線がずれている：`Q`で中止し、カメラの設置位置・ズーム・解像度を元に戻すか、改めて四隅を登録。
- Camoと通常USBカメラを切り替えた：画角や画像処理が異なるため、そのまま流用しない。

このツールは判定精度が保証されたと見なすものではなく、**見た目が一致した後も実際の車を使って区画の正誤を確認**してください。映像や設定ファイルをGitHub・Supabaseへアップロードしません。

# 2026-10-29 夜間に植え込み・ガードレール・反射を「car」と誤認する問題

今回アップロードされた夜間動画では、実車のほかに、画面端や明暗の強い背景にYOLOの車両検出枠が出ていた。**YOLOがcarというクラスを返すことは、その物体が実際に車である証明ではない。** とくに高コントラスト補正（CLAHE）はほぼ真っ暗な画面のノイズや反射を強調し、誤検出が増える場合がある。

## 変更点
- `night_vision.py`: 画面のサンプリング平均輝度が35未満の極暗所では、`auto`モードでCLAHEを適用しない。35以上58未満でのみ弱い補正を適用。元の録画動画は変更しない。`night_vision_mode`の`on/off/auto`は今までどおり利用可能。
- `night_vehicle_evidence.py`: **夜間は一定期間の連続した位置移動が確認できた車両候補だけ**、車両追跡セッションに登録する。高信頼度でも静止したままの植え込み・柵・ヘッドライト反射は、追跡・駐車確定へ進めない。カメラ検出枠は薄い灰色の`car? (UNVERIFIED)`と表示し、緑色の検証済み車両と区別する。
- 実車が車庫に接近する過程も観測できるよう、既存の6区画を囲む小さな進入判定範囲を追加。遠景などの無関係な物体は引き続き追跡しない。
- `monitor.py`: 暗所の未検証車両は`OCCUPIED`を確定させない。接触が疑われる区画は`UNKNOWN`とし、`AVAILABLE`とは判定しない。生の録画はそのまま、判定動画だけで説明表示を変更する。
- `駐車区画_判定診断.csv`の「夜間車両確認」「確認理由」に`NO_OBSERVED_VEHICLE_APPROACH`などを記録する。カメラ・モデルの誤判定をあとから検証できる。

## 現地確認（重要）
1. ノートPCのYOLOを停止し、`git pull --ff-only`で更新してから従来の`ホーム駐車場_ライブ共有.cmd`を起動する。
2. 暗い画面で動かない車っぽい誤検出は、緑色の確定枠でなく、灰色の`UNVERIFIED`枠になるはず。
3. **すでに駐車している車から録画を開始した場合、夜間は進入動作の証拠を確認できず`UNKNOWN`のままになる**。今回は「静止した何か」を車と誤認するより、安全側で未確認にする設計を優先した。夜間の実験は、カメラを先に起動し、車が進入・移動して停車する様子を連続撮影すること。
4. 実車が駐車したら`ZONE`・`STILL`・`PARKED`・`OCCUPIED`を確認する。車が映っていても確定しなければ、`駐車区画_判定診断.csv`の「監視対象」「夜間車両確認」「確認理由」「瞬間区画」を見る。
5. 運転中はスマホ・ノートPCの操作をしない。利用者への公開は判定が安定してから管理者アプリで許可する。

**限界:** この修正は夜間の誤「駐車中」を減らす保守的なルールであり、画像から「車」と「車以外」を必ず正確に見分ける追加学習済み分類器ではない。たとえば動く影や照明の変化は完全には除外できず、反対に実車がすでに停車している場合は保留になる。実際の動画での修正後の認識率は再計測が必要。信頼性をさらに上げるには、夜間の実地画像で背景・誤検出を含む教師データと、専用の車両分類/セグメンテーションモデルを用意する。

- `駐車区画_判定診断.csv`に**監視対象**・**近接区画**と`IGNORED_OUTSIDE_MONITOR_AREA`を追加。次回は実際の車両と誤認識を区別しやすい。
- 区画未確認は安全のため`UNKNOWN`を維持し、実際に未確認の枠を`AVAILABLE`とは報告しない。公開設定や本来の初期空車確認は別途行う。

注意：アップロード動画に対するコードの**オフライン再推論精度は検証していない**（この環境にローカルの学習済みモデルとカメラ設定が無い）。GitHub Actionsは合成ケースの単体・回帰テスト。夜間の反射や白飛び、ピントの物理的な問題はソフトウェアだけで完全には修復できない。

1. カメラ画面の`q`で終了、`git pull --ff-only`で更新。
2. `ホーム駐車場_ライブ共有.cmd`で起動。録画動画で`IGNORED`（監視範囲外）・`ZONE`（候補区画）・`STILL`・`PARKED`・`OCCUPIED`を確認。

# 2026-10-29: タイヤ接地点を優先した駐車枠判定と一時的な誤BLOCKED抑制

10月29日の実験動画では白い車の前方で `person` が検出され、`space_002` が一時的に `BLOCKED` となる場面を確認しました。動画だけでは人か影かを断定しません。

## 更新内容
- 車両のYOLO矩形下端＝タイヤ位置という旧方式をライブ判定から外しました。`wheel_geometry.py` が映像上の暗い円形特徴と周囲の明度差を調べ、**2個のタイヤ候補が十分に見える場合のみ**、接地点の推定値を返します。

# カメラが明るすぎて駐車枠が見えない場合（2026-10-28追加）

駐車枠の登録画面を**静止画からライブカメラに改善**しています。画像が白飛びする場合は「見えない区画」を4点登録しないでください。

1. 外付けWebカメラを駐車区画が映る方向に向けます。光源（強い空・太陽など）を画面の大部分に入れないようにしてください。日陰側から撮影したりカメラを少し下に向けることも有効です。
2. PowerShellから従来の「駐車場_アプリ連携を始める.cmd」を起動します。既存の枠があっても「再調整しますか？ [Y/n]」には Y を選んでください。
3. **リアルタイム映像**を見ながら露出を調整します。画面下部の黒い操作帯には現在の区画名と白飛びの目安が表示されます。
4. **P**：外付けWebカメラの設定画面（DirectShow方式のWebカメラのみ）。Exposure/露出のAuto/自動をOFFにして露出・必要ならGain/ゲインを下げてください。機器ごとに名称や操作が違います。
5. **-**：カメラの露出を1段暗く、**+**（または=）：明るく、**A**：自動露出へ。機器がこれらの制御を受け付けなければエラーではなく「未対応」と表示します。光学的な白飛びは画面の画像処理だけでは直せません。露出値を保存した場合はYOLO本番でも同じ露出の適用を試みます。
6. **Space**：映像を一時停止。画像の駐車枠を左クリック4回で登録（クリック1回目で自動停止も可能）。
7. **Q**：変更を保存して終了。**Esc**：区画と露出の変更を保存せず終了。
8. 1つ以上の区画が実際に映り、枠の位置が確認できるまでSupabaseの一般公開を有効にしないでください。

注意：カメラ付属アプリやWindowsの設定で露出調整が可能な機種もあります。OpenCVでカメラの詳細設定を開く機能はDirectShow方式のみ対応です。設定変更が録画本番の再接続でも持続するか、実機の録画を1分ほど行って確認してください。区画の座標と撮影範囲は設定ファイルに記録され、変更前の設定はPC内にバックアップされます。

# ノートPC＋外付けUSB Webカメラのライブ実験・自動録画（2026-10-28）

この実験では**内蔵カメラを使わず、外付けUSB Webカメラを選択**して利用します。
カメラからの録画はPCの内部に保存し、YOLOは同じ映像から駐車枠を判定します。
従来のSupabase連携・管理者/ユーザーアプリへの送信はそのまま使います。

## 操作の順番

1. ノートPCにUSB Webカメラを接続し、他のカメラ利用アプリを閉じます。
2. 初回は「ホーム駐車場_かんたん準備.cmd」を実行します。カメラ番号を入力し、**プレビューで実物の外付けカメラ映像を確認したときだけSキーを押して「外付け」と入力**してください。番号0が外付けとは限りません。
3. 指定した外付けカメラの映像に対して、実際の駐車枠の四隅をクリックして登録します。準備時のローカル判定テストから録画が始まります。
4. アプリへライブ共有する場合は「ホーム駐車場_ライブ共有.cmd」を実行。「共有」と入力後、**その日も同じ外付けカメラか映像で再確認**します。認証後の判定中は録画とSupabase更新が並行して進みます。
5. 判定画面の **qキー** で終了。録画は閉じられ、「録画フォルダを開く.cmd」で見返せます。

※カメラの番号と機器名をOpenCVだけで確実に対応付けることはできません。選択画面では間違えた番号の映像を一時的に開く可能性があります。**内蔵カメラを一切開かない条件**で試験するには、事前にWindowsのデバイスマネージャーで内蔵カメラを無効化してください（外付けカメラは無効化しない）。

## 録画の保存場所と内容

Windowsのローカル領域（通常は以下）に自動保存します。OneDrive、Supabase、GitHubへ映像をアップロードする処理はありません。

~~~text
%LOCALAPPDATA%\ParkingResearch\Recordings\
  20261028\
    20261028_140500_******\
      映像_001.mp4
      映像_002.mp4
      録画ファイル一覧.csv
      区画状態の変化.csv
~~~

- カメラ映像は**10fps・10分ごと**を初期値として分割保存（recording_fps、recording_segment_secondsで変更可）。MP4が利用できない環境ではAVIに切り替えます。**音声は録音しません。**
- 映像上部に撮影日時を表示します。区画状態の変化.csvには空き・駐車中・障害物あり・確認できないの変化と経過秒数を記録します。2つのファイルを照らし合わせて誤判定を見返せます。
- カメラの画像取得とYOLO判定を別スレッドで実行します。**YOLOの処理待ち中も録画が進みます**が、カメラ自体が取得できなかったフレームは復元されません。極端に負荷が高い場合は映像が一時的に止まったように見えることがあります。
- 途中でWebカメラが切断された場合や、空き容量が1GiB未満になった場合、録画とライブ判定を停止します。アプリ側は20秒以上更新がなければ「確認できない」とします。
- 既存の録画は**自動削除しません**。保存容量に応じて自分で整理してください。顔や車のナンバーが写る可能性があるため第三者に公開しないでください。インターネットに映像を公開する機能ではありません。
- Windowsが同期対象に設定した特殊なフォルダではなく、LOCALAPPDATAを優先して保存します。実機の保存先は画面の「【録画保存先】」で確認してください。
- ノートPCでの実カメラ・コーデック・GPU負荷の動作試験は未完了です。実験の最初に1分ほど撮り、録画ファイルをWindowsで再生できるか確認してください。

## ノートPCへの準備

- 外付けWebカメラに加え、Python、OpenCV、Ultralytics、研究で学習したbest.ptが必要です。config.jsonや録画はGitHubには含めません。

# 【2026-10-27】日光駐車場の混雑映像から追跡・空き判定を見直し（v3）

### 修正の根拠

提供された「道の駅日光駐車場ライブカメラ_ニコニコ本陣.mp4」の旧バージョンの解析結果：
**676フレーム（22.5秒）、8区画、235追跡セッション、YOLO生IDの再結合109回、追跡消失39件**。
数値は旧結果で、235台通ったという意味ではありません。枠008は「占有→空き」になり、
元映像では車が残っている可能性があるため安全側の判定が必要でした。

### v3の変更

1. **トラッカーをカメラに合わせる。** `botsort-parking.yaml` は固定カメラ向けBoT-SORT（背景移動補償なし、失踪追跡バッファ90フレーム）。`tracker_file` でByteTrackにも切り替え可能。BoT-SORTのReIDは標準で無効、外観特徴の簡易チェックは別の `stable_ids.py` で行う。
2. **同じ車両の対応を厳密化。** 生YOLOの同一IDだけを信用せず、位置・矩形IoU・色分布・時刻を評価し、フレーム内では1対1対応に限定。複数候補で曖昧なら結合しない。
3. **追跡しやすい検出と、占有と判定する検出を分離。** `tracking_confidence=0.15` をトラッカー入力に使い、占有には `confidence=0.35` 以上を要求。設定の根拠は初期仮説であり、まだ現地で最適化された値ではない。
4. **誤った空き案内の防止。** 一度車の見えた枠で車が検出されなくなった場合、8秒間は駐車中の状態を保持し、出庫を実際に追跡できなければ**「確認できない」**に戻す。無検出＝空きとは扱わない。
5. **開始時点ですでに止まっている車の駐車開始時刻は不明。** 統計上の駐車時間を捏造しない。
6. **録画実験の検証可能性。** `車両ID対応.csv` を追加し、`stable_id_reassociations`、`original_yolo_id_count`、`unverified_free_frame_blocks` などを出力。
7. **区画境界上の車両。** 車の接地位置を3点で確認。隣接枠にまたがる場合は安全側でunknownとし、空きと誤表示しない。

### 日光動画を再解析する（自宅のconfig.jsonは維持する）

最新版の `parking-vision` フォルダをPowerShellで開き、`config_nikko.json` に旧実験の8区画の座標が含まれていることを確認する。

# 駐車場の自動検知・リアルタイム共有（卒業研究）

## できること
カメラ映像から車両と人を検知します。追加学習した障害物モデルを指定すると、カラーコーン・カート・バリケードなども検出対象になります。車ごとに一時的な追跡IDを付け、移動中・駐車中・出庫中・退出済み等を管理します。駐車中と判定された時刻から駐車時間を計測します。映像はSupabaseへ送らず、区画状態と管理者用の匿名車両イベントだけを保存します。

利用者画面は約3秒ごと、管理者画面は約4秒ごとに最新状態を確認します。**WebSocket即時プッシュではなく短周期の自動更新です。**通信不良または20秒以上更新なしの区画は「確認できない」とし、空き案内には使いません。

## Windowsでの準備
管理アプリのリポジトリを取得したら、parking-vision フォルダでPowerShellを開きます。

~~~powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item config.example.json config.json
notepad config.json
~~~

すでにYOLOとOpenCVを導入した仮想環境なら、再インストールは不要です。利用中の環境で実行してください。

### 設定項目
- facility_id: 管理画面と一致する施設ID。自宅実験用は home-test-001 です。
- camera_id: 任意のカメラ名。複数カメラで同じ名前を使わないでください。
- source: USBカメラなら 0、RTSP/IPカメラなら説明書で確認した映像URL。
- supabase_url、publishable_key: 両アプリの sync-config.js と同じ公開用接続情報。秘密鍵は書かないでください。
- vehicle_model: 車両が検出できる既存の best.pt のパス、または汎用 yolo11n.pt。
- obstacle_model: コーン・カート等を追加学習した best.pt。未学習なら空のまま。
- space_uids: カメラで全体が見える区画IDのみ記入します。例：space_001～space_008。

config.jsonはGitにアップロードされない設定です。**認証パスワード、私有カメラのURL、録画を公開リポジトリへ置かないでください。**

## 1. カメラに写る区画を登録
~~~powershell
python calibrate.py --config config.json
~~~
画面の space_001 などの表示を確認し、その駐車枠の四隅を順番に4回クリックします。実際に見えない枠は s で飛ばしてください。Backspaceはクリック取り消し、rはやり直し、eは入口、xは出口の範囲指定、qで保存して終了です。カメラ角度を変えた場合、最初からやり直してください。

## 2. 通信しない検証
~~~powershell
python -m unittest discover -s tests -p "test_*.py"
python monitor.py --config config.json --preview --dry-run
~~~
空き区画、駐車車両、移動車両を映し、画面内の状態が一致するか確認します。**カラーコーン・カートは障害物学習済みモデルがない限り認識を保証しません。**

## 3. クラウドへ共有
~~~powershell
python monitor.py --config config.json --preview
~~~
Supabaseの管理者メールとパスワードを入力してください。入力したパスワードは画面に表示されず、ファイルには保存しません。管理アプリで施設を選び「カメラによる空き状況・車両追跡」を開くと、枠ごとの最新状態、追跡ID、駐車経過時間が表示されます。

**初期状態では利用者へのライブ公開はOFFです。**管理画面で実際の駐車状況と一致することを確認し、「利用者アプリへ最新の空き状況を公開」をONにしてください。公開するのは区画の状態のみです。自宅実験用施設を公開する際は、場所と利用者のプライバシーに注意してください。

## 4. カラーコーン・カート・障害物を追加学習
正解の枠を付けた画像とラベルを学習用・検証用に分けて用意し、data.example.yaml を参考に data.yaml を作成します。
~~~powershell
python train_obstacles.py --data data.yaml --device cpu
~~~
CUDA対応GPU環境を導入済みなら --device 0 が使えます。学習出力の best.pt を config.json の obstacle_model に指定してください。写真や正解ラベルは同梱していません。モデルのクラス名は traffic_cone、shopping_cart、barrier、bollard、obstacle など monitor.py の BLOCKING_NAMES と対応させてください。

## 判定のルールと限界
| 状態 | 基準 |
|---|---|
| 入場確認中 | 同じカメラに新しく写った車。入口通過の保証はない |
| 移動中 | 駐車条件を満たしていない車 |
| 駐車中 | 同じ区画で5秒以上ほぼ動かない車 |
| 出庫中 | 駐車区画から2秒以上離れた車 |
| 退出済み | 登録した出口の範囲に入った車 |
| 追跡できなくなった | カメラ内で見失った車。退出と推定しない |

車両が区画内に入ると、駐車時間の確定前でもその区画を「使用中」とします。**空き**は車も認識可能な障害物も検出されない状態が5秒以上継続した場合に限ります。見落とし・死角・逆光・夜間で誤判定し得ます。

**1台の車の追跡はカメラ1台の連続映像内のみです。**カメラをまたいで追跡IDを結びつける機能は未実装です。撮影範囲外の駐車時間も計測できません。車両セッションは管理者専用で、利用者へは配信しません。実運用前には保存期間と撮影告知のルールを設けてください。
